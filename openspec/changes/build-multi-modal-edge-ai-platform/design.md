## Context

当前仓库已经存在三个重要事实：

- `web/` 已经建立了前端工作台骨架，并完成 `Overview`、`1D`、`Image` 入口和 `1D -> Dataset` 的首个交互原型。
- `.agent` 中的计划原本同时考虑 `Data Classification` 与 `Time Series`，但当前更现实的第一阶段落点是先稳定 `1D Data Classification`，并补充结构相近的 `1D Regression`，将独立时序任务延后。
- `openspec/specs/` 目前为空，说明项目还没有平台级行为契约，现阶段最缺的是统一定义而不是局部编码。

这意味着设计必须同时满足两个约束：一是不能推翻现有 `1D -> Dataset` 已做的前端方向；二是必须从一开始就把四类任务放进同一套平台骨架中，否则后续 Image 路线会与 1D 路线产生模型、数据和接口层面的分叉。

## Goals / Non-Goals

**Goals:**

- 建立统一的平台骨架，让长期规划中的多类任务共享一致的产品结构与训练接口。
- 把当前 `1D -> Dataset` 原型纳入正式任务流，并明确第一阶段先支持 `1D Data Classification` 与 `1D Regression`。
- 以当前前端为主要推进对象，先稳定前端任务流、页面结构和交互细节。
- 抽象出“任务定义 -> 数据集定义 -> 训练配置 -> 训练执行 -> 产物导出”的通用链路。
- 为前端 Vue 工作台和后端 Python API 提供稳定的契约，降低并行开发耦合。
- 让训练输出天然适配 ESP32 端部署，而不是训练完成后再额外补格式转换。

**Non-Goals:**

- 本变更不规定具体模型结构细节，例如某个 CNN/LSTM/YOLO 变体的完整实现。
- 本变更不在 proposal 阶段确定最终训练框架选型，只定义插件化和可扩展边界。
- 本变更不覆盖端设备上的推理运行时实现，只定义训练侧必须输出的部署产物。
- 本变更不要求一次性完成全部四类任务的 UI 和训练代码，而是先建立统一骨架与阶段顺序。
- 本变更不自动启动后端代码实现；后端编码只在团队明确要求开始后再执行。
- 本变更不默认接受大范围前端重构；超过小步调整范围的前端改动需要先征求人工意见。
- 本变更当前不实现独立的 `1D Time Series Classification` 页面与流程；时序场景暂时通过用户预整理为固定长度的一维样本来兼容。

## Decisions

### 1. 采用“任务模板 + 公共训练骨架”的平台模型

平台将四类任务拆成“任务模板”，每个模板定义：

- 数据集组织规则
- 支持的标注方式
- 训练参数表单
- 评估指标
- 导出产物类型

同时，所有模板共享统一骨架：

- 前端统一工作台导航
- 后端统一训练任务入口结构
- 统一训练状态对象
- 统一训练结果摘要

这样做的原因是四类任务在数据格式上差异很大，但在“选择任务、准备数据、配置训练、执行训练、查看结果、导出部署文件”这条链路上高度一致。相比为每类任务各做一套独立流程，这种设计更利于复用和扩展。

替代方案是按 `1D` 和 `Image` 分成两套前后端系统，但这会导致 API、状态管理和导出格式割裂，不适合当前团队规模。

### 1A. 当前执行顺序采用“前端优先、后端延后编码”

当前阶段先完成前端工作台中的信息架构、任务流和交互细节，后端只保留契约级设计，不直接进入代码实现。

这样做的原因是项目当前已经有前端原型和明确的页面推进主线，而后端真实接口形态仍依赖前端任务流的稳定结果。先把前端产品面走通，能够避免过早固化后端实现。

替代方案是前后端并行编码，但在当前阶段容易造成接口反复变动和重复返工。

### 1AA. 第一阶段先开放 `1D Data Classification` 与 `1D Regression`

虽然长期规划包含独立的时序任务，但当前实现阶段先开放 `1D Data Classification` 与 `1D Regression`。这两类任务在输入形式上都可以复用“一行一个样本”的数据组织方式。对于来自时序信号的场景，当前要求用户先在平台外完成切窗与定长展开，再作为一维样本导入。

这样做的原因是 `1D Regression` 与现有 `1D Data Classification` 在数据上传、通道配置、预览交互上高度复用，而独立时序任务会立即引入窗口长度、步长、样本边界、时间列映射等复杂配置，当前前端和后端都尚未准备好承载这套额外交互与处理链路。

替代方案是同步建设 `1D Time Series Classification`，但这会显著拉高第一阶段复杂度，不符合当前收敛目标。

### 1B. 前端改动默认小步推进，重大改动先人工确认

对于现有 `web/` 页面，设计上采用增量演进策略：优先复用已有结构、局部补齐信息和交互，不主动进行大规模布局重做或导航重构。

这样做的原因是当前已有原型已经体现了团队方向，过大的改动会放大评审成本，也更容易偏离人工预期。

替代方案是直接按新抽象重做前端，但这会打断当前节奏，不符合当前协作约束。

### 1C. 整个工程采用“人工提需求、AI改动、人工评审”的默认协作模式

整个工程在执行上采用固定协作模式：由人工提出当前需求或修改建议，AI根据该输入完成改动，改动完成后交由人工评审，评审反馈再决定是否继续下一步。

这样做的原因是当前项目仍处于产品定义与实现细节不断收敛的阶段，人工评审能够及时纠偏，避免 AI 在缺少业务判断的情况下连续推进到错误方向。

替代方案是由 AI 连续多步自主推进，但这不符合当前项目对节奏控制和人工判断参与度的要求。

### 1D. 开发实现默认遵循“优先复用、按需导入、谨慎引入依赖”的约束

在实际编码过程中，默认遵循以下开发规则：

- 优先复用已有实现，避免重复造轮子；当逻辑或 UI 存在明确复用需求时，应评估并提炼为独立组件或独立模块。
- 尊重摇树优化，保持按需导入，避免引入未使用或非必要的内容。
- 安装新依赖或升级依赖前，应先核实可用的最新稳定版本，并优先采用较新的稳定版本。

这样做的原因是当前项目既在快速迭代产品定义，又需要保持前端和后端代码的长期可维护性。优先复用能够减少重复逻辑和分叉实现；按需导入能够控制构建体积和无效依赖；谨慎引入依赖能够降低后续维护和升级成本。

替代方案是按功能局部快速堆叠实现，但这会让组件、状态和依赖逐步失控，不利于平台后续扩展。

### 2. 将数据集契约上移为平台核心能力，而不是页面细节

当前 `.agent/plans/timeseries-dataset.md` 已经对 `1D` 数据集做了较多约定。设计上继续沿用这个方向，但进一步把“数据集契约”抽象成平台级能力，覆盖：

- 目录结构校验
- 列映射或类别解析
- 预览抽样
- 数据摘要
- 标签映射
- 训练输入规格

原因是训练平台的稳定性首先取决于输入数据是否可解释。把数据集契约前置，有助于在前端和后端共享同一份校验规则。

替代方案是让每个训练脚本自己读取和推断数据，但那会把错误暴露推迟到训练阶段，导致调试成本上升。

### 3. 后端采用统一训练任务请求模型，按任务类型分发执行

后端保留统一入口模型：

```json
{
  "task_family": "1d" | "image",
  "task_type": "data_classification" | "timeseries_classification" | "image_classification" | "object_detection",
  "dataset": {},
  "model": {},
  "training": {}
}
```

实现上可以是单路由分发，也可以是多个任务路由，但服务内部必须共享同一套请求/响应对象。

原因是这能让前端表单状态和后端处理链路保持一致，也便于后续加入训练历史、队列和日志能力。

替代方案是每个任务暴露完全不同的接口，但这会让前端表单、状态和结果页难以统一。

### 4. 训练输出统一采用“模型包 + 元数据”形式

每次训练完成后，平台至少输出：

- 模型文件
- 标签映射
- 输入规格
- 训练配置快照
- 指标摘要

其中“输入规格”必须足够支持 ESP32 端推理接入，例如样本长度、通道数、图像尺寸、类别列表。

原因是对端侧 AI 平台来说，单独保存一个模型文件不够，部署链路真正依赖的是完整上下文。这个设计也能避免模型导出后丢失标签和输入定义。

替代方案是只输出训练框架原生权重文件，但这对部署集成帮助很有限。

## Risks / Trade-offs

- [任务范围较大，四类任务同时定义] -> 通过“统一骨架 + 分阶段落地”控制复杂度，先完成 1D，再扩 Image。
- [数据格式差异大，统一抽象可能过度] -> 只抽象公共流程，不强行统一底层数据结构；具体字段由任务模板各自定义。
- [后端训练框架后续可能变化] -> 在设计中只固定 API 契约和产物格式，不过早绑定实现框架。
- [当前已做前端可能与最终抽象存在偏差] -> 明确将现有 `1D -> Dataset` 视为第一阶段试点，允许局部重构但保持交互目标不变。
- [ESP32 端部署约束尚未完全固化] -> 先将导出能力定义为最小模型包，后续再为具体芯片/推理引擎补专用导出器。

## Migration Plan

1. 保留现有 `web/` 导航和 `1D -> Dataset` 原型，避免中断当前开发。
2. 先补齐规格文档与任务拆解，再按规格对前端页面结构和状态模型做小步调整。
3. 若前端调整涉及明显的信息架构、导航或交互路径变化，先提交人工确认，再继续落地。
4. 在未收到“开始后端”指令前，仅保留 Python 端契约和接口设计，不进入后端代码编写。
5. 收到明确指令后，再建立统一训练请求对象和占位接口，优先跑通 `1D Data Classification`。
6. 在相同数据骨架上补充 `1D Regression` 的任务配置、训练指标和结果展示。
7. 完成统一产物清单格式，确保首个任务训练后即可导出基础模型包。
8. 在 `1D Data Classification` 与 `1D Regression` 稳定后，再与人工共同决定是否恢复独立的 `1D Time Series Classification`。
9. 以同一骨架继续扩展 `Image Classification`、`Image Object Detection`。

回滚策略：

- 如果统一抽象影响当前前端进度，可暂时保留现有页面实现，仅在接口层和文档层对齐新契约。
- 如果某类任务暂时难以落地，可冻结该任务模板，不影响其他任务继续使用同一平台骨架。

## Open Questions

- `1D Data Classification` 是否长期视为独立任务，还是后续并入更广义的 `Tabular` 能力。
- 图像目标检测首版采用何种标注格式作为平台标准，例如 YOLO TXT 还是 COCO JSON。
- 训练任务执行是同步阻塞返回，还是从第一版开始就采用异步任务和轮询状态。
- 首版模型导出优先面向哪类 ESP32 推理链路，以便确定模型包中的额外转换产物。
