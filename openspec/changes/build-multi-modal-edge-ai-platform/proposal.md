## Why

当前项目已经完成 `Vue + Vite + TypeScript` 的前端骨架，并率先落地了 `1D -> Dataset` 的可交互原型，但整体产品定义仍停留在局部页面层面。为了把平台从“单点页面演示”推进到“可持续扩展的 ESP32 端侧 AI 训练平台”，需要先补齐统一的任务边界、数据契约、训练流程和端侧产物定义。

现在推进这项变更的原因很明确：团队长期目标仍然是支持一维数据分类、一维回归、一维时序分类、图像分类、图像目标检测等任务，但当前阶段应先收敛到可落地范围。如果没有平台级 proposal，后续前端交互、Python API、训练脚本和模型导出会各自演进，难以复用也难以保持一致。

整个工程默认采用“人工提出需求，AI改动，人工评审”的协作方式推进。

## What Changes

- 定义一个统一的平台任务矩阵，长期覆盖 `1D Data Classification`、`1D Regression`、`1D Time Series Classification`、`Image Classification`、`Image Object Detection` 等任务。
- 明确第一阶段先聚焦 `1D Data Classification` 与 `1D Regression`，当前前端页面已完成两类任务的 `Dataset` 入口与基础预览能力，独立时序任务暂不进入实现。
- 明确平台的信息架构，统一前端工作台中的任务入口、任务级页面结构、数据集页与训练页的职责边界。
- 明确当前实施节奏以前端为优先，后端设计可以先定义契约，但后端代码只在团队明确发出开始指令后再进入编写阶段。
- 约束前端实现采用小步迭代方式推进，默认不做大幅结构改动；一旦需要明显调整现有页面结构、交互路径或视觉布局，必须先征求人工意见。
- 定义平台任务的数据集导入、校验、摘要、预览和标签解析契约，保留当前 `1D -> Dataset` 文件夹上传原型作为第一阶段落地点。
- 统一 Python 后端训练 API 的请求/响应结构、任务路由、训练状态返回和错误处理约定。
- 定义训练任务的公共配置模型，包括任务类型、数据输入规格、模型预设、训练参数和评估结果摘要。
- 定义面向 ESP32 端部署的训练产物边界，包括模型文件、标签映射、输入规格和训练报告。
- 将当前已完成的前端原型视为平台第一阶段实现，而不是孤立功能，后续新增任务按同一骨架扩展。

## Capabilities

### New Capabilities
- `multi-task-workspace`: 统一管理 1D 与 Image 两大入口下的四类训练任务及其页面流程。
- `dataset-contracts`: 定义四类任务的数据集导入、校验、预览、摘要和标签映射规则。
- `training-job-orchestration`: 定义统一的训练任务配置、提交、执行状态和结果展示接口。
- `edge-artifact-packaging`: 定义面向 ESP32 端侧部署的模型导出产物和元数据清单。

### Modified Capabilities

None.

## Impact

- 影响前端 `web/` 的导航结构、任务页结构、数据集页面和训练页面抽象。
- 当前前端页面需与实际能力保持一致，已实现页面先聚焦 `1D Data Classification`，后续在同一阶段补充 `1D Regression`，不提前展示未实现的独立时序任务入口。
- 影响未来 Python API 的接口设计，包括 `GET /health`、任务级训练接口和统一响应格式，但当前阶段仅定义后端契约，不默认进入后端编码。
- 影响训练脚本的输入参数组织方式、模型预设注册方式和结果输出结构。
- 影响后续端侧部署流程，需要训练输出携带输入规格、标签映射和模型文件等元数据。
- 当前不要求立即完成全部任务实现，但要求所有后续开发都以这套平台级契约为基线推进。
- 当前前端改动需优先保持现有原型连续性，超出小步演进范围的改动需要先经过人工确认。
